## 1. 先厘清一个常见误解

**"据点等级"不是据点自己的属性。**

玩家嘴里说"我住 3 级区"，系统里其实发生的是：

```
玩家住哪个聚落 → 该聚落属于哪个区 → 该区是什么 Tier → 该 Tier 的经济参数
```

所以：
- **没有"聚落升级"这件事**（不存在"把 1 级聚落升到 2 级"）
- **只有"搬家"**（从 1 级区搬到 3 级区）
- **聚落本身没有等级字段**（`SettlementDescription` 只是枚举项）

**设计含义**：等级是**空间属性**，不是**对象属性**。这让"升级"变成"搬家"——一次完整的内容迁移，而不是点个按钮。`【推断】`

## 2. 三个等级概念的玩家语言

| 玩家说 | 系统里 | 玩家实际关心 |
|---|---|---|
| "我在 3 级区" | `TierDescription.Tier3` | 能买 3 级货、洗钱快、税高 |
| "我在 Highlands" | `Sector9` | 能保资产（州末豁免）、帮战最凶 |
| "这个赛季" | `RealmVersion.V0` | 当前只有第 0 赛季 |
| "这个州开了多久" | `RealmEntry.StartTs` | 老州/新州 |

**关键区分**：**"区等级" ≠ "区名"**。Tier 1/2/3 是标签，Highlands 是名字。Highlands 恰好是 Tier 3（中央区），但"Highlands"这个名字承载了"州末保资产"的特殊规则（见 D01）。`【推断】`

## 3. 一个 Tier 到底给了玩家什么（玩法化解读）

`TierParams` 的 7 块参数，翻译成玩家语言：

| 参数块 | 玩家语言 | 玩家决策 |
|---|---|---|
| `IsEnabled` | "这个区开没开" | 能不能选 |
| `CanBuySettlement` | "这区能不能买聚落" | 能不能当业主 |
| `SectorSettlementsCount` | "这区有几个聚落" | 有多少选择 |
| `ClanBattleBetMinAmount` | "打这区要押多少" | 帮派要不要打 |
| `LaunderingDirtyCashPerPeriodModifier` | "这区洗钱快不快" | 生产型玩家选这区 |
| 4 个 tax + 2 个 bonus | "这区税高不高" | 业主选这区 |
| 5 张价格表 | "这区地价/聚落价" | 所有人都关心 |

**设计洞察**：**Tier 越高 ≠ 越好**。
- 高 Tier：物品好、洗钱快、但税高、地价贵、帮战凶
- 低 Tier：物品差、洗钱慢、但税低、地价便宜、安全

这正是"空间专业化"的基础：**做武器的去军工厂区，做毒的区，养老的去 1 级区**。`【推断】`

## 4. 玩家旅程：等级如何驱动"搬家"

| 阶段 | 玩家状态 | 等级驱动 | 体验 |
|---|---|---|---|
| 新手 | 1 级区 | 教程给的 Tier1 地券只能用在这 | "先有个家" |
| 成长 | 想买 2 级货 | 需要搬去 2 级区 | "我得换地方" |
| 中期 | 想当业主 | 需要 2/3 级区（如果 `CanBuySettlement` 允许） | "我要有自己的聚落" |
| 后期 | 想保资产 | 需要搬去 Highlands（Tier3 中央区） | "我要最强" |
| 终局 | 州末清算 | Highlands 豁免 | "我赌对了" |

**核心体验**：**等级不是数值成长，是地理迁移**。玩家每次"升级"都要做一次"搬家"决策，而搬家有成本（地券、迁移、社交关系）。`【推断】`

## 5. 数值框架（本地真值 + 推断）

### 5.1 已确认（`【原作-实证】`）

- Tier 只有 3 档
- 区只有 10 个
- 每档 Tier 有 5 张价格表 + 4 个税率 + 1 个洗钱乘区 + 1 个帮战下限 + 1 个聚落数
- `TierExtensions.CheckTierRequirement(actual, required)` 是唯一的门槛比较
- 当前只有 `RealmVersion.V0`

### 5.2 推断的数值梯度（`【推断】`，复刻起步）

| 参数 | Tier1 | Tier2 | Tier3 |
|---|---|---|---|
| 地券价格（相对） | 1× | 3× | 10× |
| 聚落价格（相对） | 20× | 60× | 200× |
| 洗钱速度乘区 | 1.0 | 1.25 | 1.5 |
| 业主税率 | 5% | 8% | 12% |
| 购买税 | 2% | 4% | 8% |
| 帮战下注下限 | 低 | 中 | 高 |
| 每区聚落数 | 多 | 中 | 少 |
| `CanBuySettlement` | true | true | true（仅 Highlands？） |

**设计校验**：Tier3 的"高税+高地价"必须被"高洗钱速度+物品等级+州末豁免"补偿，否则没人住。`【推断】`

## 6. 三个必须讲清的设计决策

### 6.1 为什么"等级"要绑定在"区"而不是"账号"

- 如果等级在账号上 → 玩家会"刷等级"，然后永远待在高档区 → 低级区变死区。
- 如果等级在区上 → 玩家必须**物理迁移**才能获得高级内容 → 低级区永远有人（新手/养老）。
- **副作用**：高档区会拥挤，低档区会空。ROB RUN 用"每区聚落数递减"（`SectorSettlementsCount`）来限制高档区容量。`【推断】`

### 6.2 为什么没有"聚落升级"

- 如果有 → 玩家会把 1 级聚落养成 3 级，然后**所有聚落最终都变成 3 级** → 等级失去意义。
- 没有 → 等级是"地图上的固定分块"，永远有梯度。`【推断】`

### 6.3 为什么当前只有 V0（一个赛季）

- 版本化框架已经完整（`RealmVersionedValue` / `*RealmVersion0/1` 类都在）
- 但 `RealmVersions` 只注册了 `V0`
- **含义**：ROB RUN 的"赛季"目前是"州寿命"（7 天），不是"数值版本"。版本化是**留给未来内容更新的钩子**。`【推断】`

## 7. 与其他系统的耦合

| 系统 | 耦合方式 |
|---|---|
| 产权 | 地券档位必须匹配区 Tier；买聚落受 `CanBuySettlement` 控制 |
| 经济 | 价格/税率/洗钱速度全在 `TierParams` |
| 物品 | 物品有 Tier 要求，`CheckTierRequirement` 判定 |
| 帮战 | 下注下限、帮战分档 |
| 地图 | 区颜色/盾徽/卡片 `tierSymbol` |
| 州末 | Highlands（Tier3 中央区）是唯一豁免通道 |

## 8. 反作弊与边界情况

| 风险 | 防护 |
|---|---|
| 低档区玩家买高档物品 | 服务端 `CheckTierRequirement` |
| 用低级地券租高级区 | Tier 匹配校验 |
| 跨区"蹭"高档商店 | 商店/黑市有位置限制（`vendor_tree_locked_by_*`） |
| 高档区被少数人垄断 | `SectorSettlementsCount` + `OwnedSettlementConfig.MaxCount` |
| 版本切换时玩家资产 | 州末清算（见 D01） |

## 9. 测试边界（本系统 14 条）

1. Tier1 玩家买 Tier2 物品 → 拒绝 + 正确文案
2. Tier2 玩家买 Tier1 物品 → 允许（"或更高"语义）
3. Tier1 地券租 Tier2 区 → 拒绝
4. Tier2 地券租 Tier1 区 → 允许？（需确认"必须匹配"还是"≥"）
5. `CanBuySettlement=false` 的区 → 购买按钮禁用
6. `IsEnabled=false` 的区 → 不出现在地图/不可进
7. 一个 Tier 的 5 张价格表都能查到（不返回空）
8. `SettlementOwnerTaxBonusFrom > To` 的异常配置 → 不崩
9. `RealmVersion.Empty` 时取参数 → 走兜底
10. `CheckTierRequirement(Tier3, Tier1)` → true
11. `CheckTierRequirement(Tier1, Tier3)` → false
12. 换 Tier 区后，已购买的 Tier1 物品还能用（物品不回收）
13. 换 Tier 区后，商店列表变化正确
14. 地图卡片显示 `tierSymbol`（ⅰ/ⅱ/ⅲ）与区一致

## 10. 复刻时的三个"反直觉决定"

1. **等级绑在区上，不绑账号** —— 这是让低级区活着、让高级区稀缺的关键。
2. **没有聚落升级** —— 一旦允许升级，所有聚落会趋同，梯度消失。
3. **Tier 越高越"贵"** —— 高 Tier 必须收更高的税/地价，否则所有人挤进 3 级区。

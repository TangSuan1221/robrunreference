# D11 · 交互 UI 与目标提示（系统策划）

> **对应技术文档**：`../tech/11_交互UI与目标提示_技术实现.md`
> **标记**：`【原作】` / `【推断】` / `【补全】`

---

## 1. 交互 UI 的唯一目标

> **让玩家在任何一个瞬间，都知道"我现在能对眼前这个东西做什么"。**

这不是 UI 美化问题，是**认知负荷问题**。ROB RUN 的解法是三段式：

```
[这个东西叫什么] + [我能做什么] + [按什么键]
     ↑                    ↑                ↑
   目标提示            动作动词         输入提示
```

**设计铁律**：
> 玩家不应该需要"试"才知道能不能交互。**不能交互时也要说明原因。**

---

## 2. 玩家旅程：一次"撬箱子"的交互

| 步 | 玩家 | UI 反馈 | 设计点 |
|---|---|---|---|
| 1 | 看向箱子 | 出现"储物箱"标签 | 目标名 |
| 2 | 走近 | 出现"按 E 开箱" | 动作提示 |
| 3 | 但箱子已被撬开 | 提示变"Already breached" | **不可用原因** |
| 4 | 换一个能开的箱子 | "按住 E 撬开（15 秒）" | **时长预告** |
| 5 | 按住 E | 进度条 + 音效 | **进度可见** |
| 6 | 松手/走开 | 进度回退 + 提示消失 | **打断反馈** |
| 7 | 撬开 | 箱子打开 + 掉落物 | **结果** |

**关键体验**：**第 4 步的"时长预告"**。玩家必须知道"要撬多久"，才能决定"要不要撬"。

---

## 3. 五种交互类型的 UI 策略

| 类型 | 例子 | UI 策略 |
|---|---|---|
| **即时** | 开门、开灯 | 只需"按 E" |
| **长按** | 撬箱、捡钱、洗钱 | 必须显示**进度条 + 剩余时间** |
| **共享** | 储物箱、货架 | 多人可同时，**无需提示"有人在用"** |
| **独占** | 藏身点、衣柜 | 有人用时显示"Cover occupied" |
| **排队** | 交易商、ATM | 有人用时显示"Wait until the seller is free" |

`【实证：类/文案；推断：分类】`

---

## 4. 目标提示的"三态"

| 态 | 显示 | 例子 |
|---|---|---|
| **可用** | 动作 + 按键 + （长按）时长 | "Hold E to breach (15s)" |
| **不可用（有原因）** | 原因文案 | "{0} required in the inventory" / "Cannot edit during raid block" |
| **无目标** | 不显示 | 看向空气 |

**为什么"不可用也要显示"**：
- 如果只显示"可用"，玩家会不断"试"
- 显示原因 = 教玩家"你需要什么"
- 原因文案本身就是**教学**（`breach_unavailable_because_of_item_is_missing` = "需要 {0}"）

`【推断】`

---

## 5. 32 种长按动作（这是局外系统的"动词表"）

ROB RUN 的 32 种互斥进程，翻译成玩家动词：

| 类别 | 动作 |
|---|---|
| **变身** | 变身罪犯（BecomeRobber） |
| **撬/开** | 撬箱（Unlock）/ 撬锁（UnlockWithLockpick）/ 撬保险箱（CloseSafe）/ 撬防御块（RaidDefenseBlock）/ 撬安全面板（HackSecurityPanel） |
| **拿** | 拿货物（TakeCargo）/ 拿战利品（TakeLootObject / TakeLootNode）/ 拿钱（TakeCash）/ 拿逮捕战利品（ArrestLoot） |
| **修** | 修安全面板（RepairSecurityPanel）/ 修防御块（RepairDefenseBlock）/ 修被撬物（RepairBreachObject）/ 修洗钱电缆（RepairLaunderingCable）/ 修充电（ChargeCumulativeItem） |
| **装/拆** | 装钻头（SetDrill）/ 拆钻头（RemoveDrill） |
| **人** | 逮捕（ArrestTarget / ForceArrestTarget）/ 解铐（UncuffTarget）/ 复活队友（ReviveCharacter）/ 补装备（RefillEquip） |
| **躲** | 进藏身点（UseHideObject）/ 检查藏身点（CheckHideObject） |
| **基地** | 用急救柜（FirstAidCabinetUse）/ 收充电奖励（CollectChargedItemReward）/ 驱逐（Evict）/ 清理大便堆（RemovePoopPile）/ 获取访问权（GetAccess）/ 重置访问权（ResetAccess） |
| **地点** | 用兴趣点（UsePointOfInterest） |

**设计含义**：**32 个动词 = 32 种"玩家能做的事"**。如果某个系统没有动词，它就不该有交互。`【推断】`

## 6. 三种"占用"的体验差异

| 占用类型 | 数据结构 | 玩家体验 |
|---|---|---|
| **共享** | HashSet | "我可以和别人一起看" |
| **独占** | 单值 | "有人占了，我等" |
| **排队** | 单值 + 队列 | "前面还有 2 人" |

**关键决策**：
- 储物箱 → **共享**（否则两个人同时开箱会互相踢）
- 藏身点 → **独占**（否则两个人叠在一起）
- 交易商 → **排队**（否则两个人同时交易会刷单）

`【实证+推断】`

## 7. 弹窗的"单例"规则

**原作**：`ModalDialogModel.OpenDialog(data)` / `IsOpened(data)` / `CloseDialogIfOpened(data)`

**规则**：
1. 同一个弹窗不重复打开（`IsOpened` 判断）
2. 状态变化时**强制关闭**（如 Raid Lock 生效 → 关闭建造面板）
3. 弹窗内可以有子弹窗（Builder 模式）

**为什么重要**：如果弹窗可以重复打开，会出现"叠了 3 层同一个对话框"的 bug。`【推断】`

## 9. 反作弊与边界情况

| 风险 | 防护 |
|---|---|
| 用 UI 卡"同时开两个弹窗" | `ModalDialogModel.IsOpened` |
| 撬锁时切屏卡进度 | 服务端计时 + `TryFinishPrediction` |
| 两人同时开同一箱互相踢 | 引用计数（共享） |
| 独占点被"卡"住 | `HideObjectRules.ExtractCharacterOutOfHideObject` 强制弹出 |
| 断线后占用未释放 | `SessionOccupancyRegistry` 批量释放（既有文档） |

## 10. 测试边界（本系统 20 条）

1. 看向可交互物 → 出现目标提示
2. 看向不可交互物 → 无提示
3. 不可用时 → 显示原因
4. 长按 → 进度条 + 时长
5. 长按中断 → 进度回退
6. 两人开同一箱 → 不关
7. A 走后 B 还在 → 不关
8. 两人抢同一藏身点 → 第二人被拒
9. 交易商被占用 → "Wait until the seller is free"
10. 弹窗打开时 Raid Lock 生效 → 自动关闭
11. 同一弹窗重复打开 → 不叠加
12. 32 种长按动作各有提示
13. 提示位置跟随物体
14. 目标重叠时显示优先级最高的
15. 断线重连 → 占用状态恢复/释放
16. 独占物被摧毁 → 里面的人被弹出
17. 输入模式切换（键鼠/触屏）→ 提示文案变化
18. 排队场景 → 显示队列位置
19. 弹窗内子弹窗 → 层级正确
20. 触屏长按 → 进度环而非进度条

---

## 11. 复刻时的三个"反直觉决定"

1. **不可用也要显示原因** —— 直觉上"不能交互就不显示"，但那会让玩家不断"试"，且错过教学机会。
2. **储物箱必须共享打开** —— 直觉上"一个箱子只能一个人开"更简单，但那会在多人据点里互相踢。
3. **弹窗必须单例** —— 直觉上"每次 Open 都新建"更简单，但那会叠加出 bug。

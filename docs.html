多人联机据点系统 · 详细策划案 v1.0

方法论：REA（Reverse Engineer Anything）—— Observation / Inference / Unknown 三级证据纪律，对 ROB RUN（Steam appid 4262460，Unity 6000.3.18f1 / IL2CPP / metadata v39）做二进制级逆向，取其据点系统的结构，产出一份可直接开工的策划案。

证据标记（全文统一）：
- 【实证】= 直接从 GameAssembly.dll / global-metadata.dat（dump.cs 行号可查）/ Addressables ScriptableObject / Unity Localization StringTable 里读到的原始事实
- 【推断】= 由 ≥2 处实证交叉推出、原作未明写的设计意图
- 【补全】= ROB RUN 没有、或明确标注 "in development" 的部分，为让方案成型而做的原创设计
- Unknown = 服务端下发、本地二进制里不存在

一句话结论：ROB RUN 的据点不是"仓库"，而是一台架在公共地图上、产权可转让、产出靠时间锁、脆弱性靠突袭窗口表达的经济引擎。它只做了"个人地块 + 聚落公共建筑"两形态，没有做帮会共建据点——这正是多人联机版本的差异化空间（见 §11）。

0. 先定义清楚：什么叫"据点"

拆到最小，一个据点必须同时具备四件东西，缺一件就退化成别的系统：

要素含义ROB RUN 怎么表达缺了会变成
产权（Property）这块地在数据库里属于谁，可转让OwnedSettlementData / Plot 归属字段 + rent sign（RentSignModel, dump.cs:160520）公共仓库
产出（Yield）占着它就能持续产出洗钱台 / 货运台 / 生产台 / 采集台，全部是 TickPeriod 驱动装饰品
脆弱性（Fragility）别人能来打，且打了有收益DefenseBlock + raid lock + 掠夺价值公式免死金牌（经济崩）
容量（Capacity）单人多占的硬上限OwnedSettlementConfig.MaxCount、ExpiringResource 配额一家独大（滚雪球）

设计铁律：任何一个据点的每小时被动产出必须 ≤ 它每小时被掠夺的期望损失，否则玩家最优解是无限扩地而不是在线。ROB RUN 用"产出必须回去取 + 取的时候人在可被入侵的空间里"解决这件事（§7.4）。

【推断】这三个值就是"软上限"的全部。它们的相对大小决定了游戏的政治形态：

  • MaxCount × 聚落数 < 玩家数 → 必然有大量无地玩家 → 租房市场成立

【推断】单轴对抗（Defense vs Breaching）而不是"血量/伤害" 的好处：

  • 时间可预测：撬开时间 = f(Defense − Breaching)，入侵者能在出发前算清楚"要带几级解码器"
  • 防守方可投资：升级模块 → 时间线性变长 → 劝退低投入入侵者
  • 不产生"打了一半血白打"的挫败

【补全】核心公式：

破门耗时 T(秒) = clamp( BASE / (1 + k·(Breaching − Defense)), T_min, T_max )
  BASE = 120s, k = 0.35, T_min = 25s, T_max = 900s
若 Breaching < Defense，则 T = T_max（打不动，需回去换解码器）

设计校验：解码器 3 档 × 防御模块 3 档 → 9 种组合，T 落在 25s–900s，跨度 36 倍，足以让"要不要来"成为真决策。

11. 【补全】多人联机据点：帮会共建据点（Clan Stronghold）

ROB RUN 没有这一层。这是本方案的核心原创设计。

11.1 为什么原作没做，而我们要做

ROB RUN 的社交是"个人 + 帮派争区"，据点永远是一个人的家。这在单机体验上很干净，但在多人联机下缺了一块：没有"我们一起拥有一块地"的体验。

帮会据点解决三件事：

  1. 协作建造（多人共建一个东西）
  2. 协作防守（帮战之外的日常防御）
  3. 共享产出（帮会金库/军械库）

11.2 帮会据点规格

项规格
数量每帮派 1 个（与 ClanConfig 绑定）
位置帮派占领的 District 内，选一个 Settlement 的公共空地
前置帮派已控制至少 1 个 District（延续 realm_conquest_sector_dialog_condition_3 的"邻接推进"逻辑）
地块尺寸个人地块的 3 倍（12×12 网格 vs 4×4）
核心建筑Clan Hall（帮会大厅）×1 —— 不可拆，帮派解散才消失

11.4 帮会据点的攻防规则【补全】

帮会据点 = 可被攻击，但只在「帮战期间」或「宣战状态下」
  ├ 平时（未宣战）：不可被 PvP 攻击，但可被 NPC 事件（警察突袭）攻击
  ├ 宣战中：可被敌对帮派攻击，Raid Lock 时长 ×2
  └ 帮战期：完全开放，掠夺收益归攻击方帮会金库（不是个人）

为什么平时不可攻？ 因为帮会据点是"集体财产"，如果 24 小时可攻，帮派会被迫 24 小时值班，变成负担而不是乐趣。只在宣战窗口开放 = 把"值班"变成"约架"。

11.5 帮会据点的产出分配【补全】

帮会据点总产出 P_total（每小时）
  ├ 40% → 帮会金库（可用于建造/军械）
  ├ 40% → 按「本周贡献点」分给成员（个人）
  └ 20% → 留存（帮战储备金，宣战时解锁）

贡献点来源：建造投入 / 参与帮战 / 参与防守 / 上缴物资

设计意图：让每个人都能算出"我多干一小时，我能多拿多少"，把帮派从"情感组织"变成"可计算的合作组织"。

三条反直觉定案：

  1. 抢钱绝不锁物体 —— CashLootNodeModel.TakeCash(int amount) 是扣减式。两人同抢 800 应得 500+300，而不是赢者通吃。这是时间竞争而非系统竞争，前者有戏剧性。
  2. 撬门允许协力加速 —— 进度是物件级的，totalBreaching = Σ 所有撬门者的 Breaching 值。这让"叫队友一起来"成为真实战术。
  3. 读操作零 RPC —— ROB RUN 的 L2 类（大部分基地交互）不发任何服务端消息。这是它能在单 State 塞下大量玩家的关键，别给读操作加 RPC。

两个必须做对的技术点：

  • 断线清理：必须有 SessionOccupancyRegistry 按 sessionId 索引全部占用，断线时批量释放。漏了就是"有人永远占着某个坑"（竞态 R10）。
  • 外力清扫：独占锁必须有"持有者被外力清除"的路径。实证 HideObjectRules.ExtractCharacterOutOfHideObject(characterId, stateModel, worldEntitiesModel, hiddenCharacters)——物体被毁时要强制把里面的人弹到 HideObjectDescription.HideOutPosition，不能等他自己发 Leave。

附录 B：可直接照抄的 12 条设计规则

多人交互物占用 · 实现规格 v1.0

配套文档：多人联机据点-详细策划案.md。本文只解决一个问题：

两个及以上的玩家同时想动同一个交互物，系统怎么办？

这是多人化过程中最容易低估、也最容易推倒重做的一块。ROB RUN 用一套非常克制的三层锁模型解决了它，全部机制可在 dump.cs 里逐行验证。本文先还原原作的架构，再给出我们要落地的定案。

0. 先把"占用"拆成四类问题

不要用一个方案打四个问题。这四类的正确解法完全不同：

类场景冲突本质正确解法
C1 同一物体 · 同一功能两个玩家同时开同一个储物箱不需要互斥，需要共享视图共享打开态 + 引用计数
C2 同一物体 · 不同功能A 开引擎盖，B 开后备箱空间上可并行分区占用（每区独立锁）
C3 同一物体 · 互斥功能一个人藏进衣柜，另一个也要藏物理上只能一个独占占用（单值槽位）
C4 同一玩家 · 互斥动作一个人不能同时撬锁和捡钱玩家自身状态机角色级互斥进程

关键认知：ROB RUN 把 C4 做成了全局强制层（每个玩家永远只有一个"进程"），而 C1/C2/C3 按物体类型分别处理。这个分工是整套架构的骨架。

2.1 真正的多人原语【实证：dump.cs:174892】

csharp
// Models.Models.InteractableObjectOpened
public class InteractableObjectOpenedModel {
    private readonly IPrimitiveData<bool> _data;                  // 0x10  ← 会被网络同步的"是否打开"
    private readonly HashSet<int>         _interactingCharacters; // 0x18  ← 本地维护的"谁正在交互"

    public bool IsOpened { get; }

    public bool ContainsInteractingCharacter(int entityId);
    public void AddInteractingCharacter(int entityId);
    public void RemoveInteractingCharacter(int entityId);
    private void UpdateOpenedState();   // 集合非空 → _data = true
}

这是整个多人占用架构里最漂亮的一段。 它解决的问题是：

玩家 A 打开了箱子，箱子在世界里视觉上要"开盖"。玩家 B 也走过来打开同一个箱子。玩家 A 关掉界面走了。箱子该不该盖回去？

朴素做法是给箱子一个 isOpened 字段，谁开谁关都写它 → A 走的时候箱子盖回去，但 B 还在看，视觉炸了。

ROB RUN 的做法是 bool + HashSet<int> 双结构 + 引用计数推导：

AddInteractingCharacter(B)  → HashSet = {A, B} → UpdateOpenedState() → IsOpened = true
RemoveInteractingCharacter(A) → HashSet = {B}   → UpdateOpenedState() → IsOpened = true  ← 关键
RemoveInteractingCharacter(B) → HashSet = {}    → UpdateOpenedState() → IsOpened = false

为什么用 HashSet 而不是 int Count？

  • 用 Count 会允许同一玩家重复 Add 导致计数虚高（A 连按两次 → Count=2 → A 走一次还是打开）
  • 用 HashSet<int> 天然幂等：重复 Add 无效，Remove 不存在的不报错
  • 而且能直接回答"我是不是正在交互"（ContainsInteractingCharacter）

7.2 PredictionExtraTimeModel：为什么需要它【实证】

它出现在 Initialize(...) 参数和每个 handler 的构造器里。

【推断】用途：客户端在本地预测"我按满进度条了，动作成功"，但服务端还没确认。如果客户端立刻播放成功动画（比如箱子开了），而服务端在 20ms 后回"你其实被打断了"，就会出现视觉回滚——玩家看到箱子开了又关上。

PredictionExtraTimeModel 提供一档额外的"等待容差"：

csharp
// 客户端
bool TryFinishPrediction(long now, BattleCharacterModel characterModel) {
    // 不是 now >= endTs 就算成功，而是 now >= endTs + extraTime
    return now >= endTs + _predictionExtraTimeModel.ExtraTime;
}

多等一拍，让服务端的打断消息有机会先到，避免视觉回滚。

7.3 我们的实现定案

状态机（客户端每个角色一份）：
  Idle ──按下──▶ Requesting（本地已播进度条，未确认）
    │                    │
    │                    ├──收到 Confirm ──▶ Active（进度条权威）
    │                    └──收到 Reject  ──▶ CancelFade（进度条淡出，不播成功）
    │
  Active ──完成/打断──▶ Idle

规则：

  1. 客户端立即播进度条（不等服务端）——否则高 ping 玩家体验灾难
  2. 完成的那一刻不立即结算，等 endTs + extraTime
  3. 收到服务端 Reject 时，进度条淡出（120ms）而不是瞬间消失
  4. 所有 *Stop 命令必须带 requestId，服务端按 requestId 幂等处理

8. 12 个必须处理的竞态（工程清单）

每一条都要写单测。这些都是上线后才会炸、但炸了就很难查的问题。

R1 · 双人同时进入同一藏身点

t0  A 客户端按下 Hide，本地预测 Hide(entityId) → 角色消失
t0  B 客户端同时按下 Hide
t1  服务端按到达顺序处理：A 成功（_entityId = A），B 失败
t2  B 客户端收到 Reject → 必须回滚角色可见性

坑：B 在 t0–t2 之间是"本地看不见自己"的状态，回滚时如果只改 IsHidden 不改相机/碰撞，会卡在墙里。
解法：IsHidden 单一真值，相机/碰撞/Collider 全部订阅它推导，禁止各处直接改。

R2 · 藏在物体里，物体被摧毁

A 藏进衣柜 → 衣柜被炸掉
→ HideObjectRules.ExtractCharacterOutOfHideObject 强制清扫
→ A 的 IsHidden = false，位置 = HideObjectDescription.HideOutPosition

坑：如果只清 IsHidden 不传位置，A 会卡在物体原本的坐标里。
解法：HideObjectDescription 里已经有 HideOutPosition / HideInPosition（dump.cs:95363），清扫时必须用 HideOutPosition。

R3 · 两人同时撬同一扇门

A 开始撬 → 进度 30%（进度在物体上）
B 加入撬 → 进度按 A+B 的 Breaching 累加
A 被打断 → 进度回退到 A 贡献的部分

坑：如果进度不记录"谁贡献了多少"，A 被打断时无法正确回退。
解法：进度结构必须是

csharp
class BreachProgress {
    Dictionary<int /*characterEntityId*/, float> _contributions;
    float Total => _contributions.Values.Sum();
}

R4 · A 撬到 50% 走开，B 接手

定案：进度保留，不回退（除非超时）。
理由：撬门是物理进度（门上真的有洞），不应该因为换人就归零。
补充：进度在 10 分钟无任何人撬 后开始以 5%/分钟衰减，防"撬到 99% 长期挂着"。

R5 · 玩家开着箱子时被击倒

A 正在看箱子（L2 AddInteractingCharacter 已加入）
→ A 被击倒 → CharacterValidationModel 失效
→ 必须发 RemoveInteractingCharacter(A)

坑：击倒路径如果不经过 handler 的 IsStop，A 就会永久留在 HashSet 里，箱子永远"开着"。
解法：IsStop 必须覆盖"角色有效性"判据（实证：IsStop 签名里就有 CharacterValidationModel）。

R6 · 开箱期间 raid lock 激活

定案：锁激活时不关闭已有界面（读操作无害），但拒绝所有写操作（建造/取放）。
理由：界面闪断是极差的体验；而写操作有服务端校验兜底。
实证支持：ResetDialogByRaidLockUpdater（dump.cs:300611）的存在说明原作对某些对话框是强制关闭的——但那只针对建造类对话框（因为槽位状态会变）。读类界面（储物箱浏览）不关。

R7 · 三个玩家同时冲向同一个交易商

定案：服务端维护一个 busyEntityId，先到者拿。其余进入排队队列（按请求到达时间排序）。
释放：交易完成 / 主人离开 5m / 超时 120s。
超时是必须的：否则一个人挂机开着交易界面，全服都被堵。

R8 · 洗钱台被 A 打开，B 把它拆了

定案：拆除操作（建造槽位 L3）需要检查"该实体是否被他人交互中"。是则拒绝，文案用现成的 unavailable_by_use_again。
但注意：这不是安全边界——如果 B 是入侵者，他应该能拆（这正是掠夺）。所以规则是：

  • 房主侧操作：被占用时拒绝（防误操作）
  • 入侵者侧操作：被占用时允许（打断防守方的作业是战术）

R9 · 车辆的 3 个 holder 被 3 人同时开

定案：天然支持，因为 holderType 是 3 个独立键。
唯一冲突点：3 号玩家想开车。规则：任一 holder 打开时车辆禁止启动（unavailable_in_the_car 反向判定）。

R10 · 断线重连后占用残留

A 撬锁到 40% → 断线
→ 服务端检测到 A 断开 → 必须主动清理 A 的所有占用：
   · 所有 L3 物体的 _entityId == A → Unset()
   · 所有 L2 的 HashSet 里移除 A
   · A 的 ProlongedInteractionModel.Stop()
   · 所有 BreachProgress 里移除 A 的贡献

坑：这是最容易漏的一条。漏了会导致"有人永远占着某个坑"。
解法：服务端有一个 SessionOccupancyRegistry，按 sessionId 索引该会话持有的所有占用，断线时批量释放。

R11 · 双人同时抢同一堆钱

定案：不锁，扣减式（TakeCash(amount)）。

2 深加工亏钱 → 不是调价，是换渠道

ROB RUN 的事实（[观] dump.cs:118184） —— CargoDescription 有三套独立的钱，一件货可同时挂多套：

csharp
int  <ArrestCoinsReward>;        // 渠道 A：上交/逮捕
int  <ExchangeCoinsReward>;      // 渠道 B：走私商直接卖
int  <ExchangeCumulativePoints>; // 渠道 B'：走私商累积点数
long <ExchangeTime>;             // 该渠道的耗时
Func<CargoDescription> <ExchangeCargoFunc>;          // 换出什么
Func<CargoDescription> <ImprovedExchangeCargoFunc>;  // 升级后换出更好的
Func<CumulativeCargoDescription> <CumulativeCargoFunc>;
long <TakeTime>;  long <OpenTime>;                   // 每个动作独立时长

硬晶体自己的描述就写明了这套逻辑（out\l10n_base_keys.txt）：

cargo_hard_crystal_1_description = "Valuable as is, but can also be packaged at a
Lab Bench for retail sale."

打包的目的不是变贵，是换渠道：原料走批发（快、单价低），成品走零售（慢、单价高）。
深加工真正的回报是 ImprovedExchangeCargoFunc——能换到市面上买不到的东西。

33000~82500 vs 27500~66000 的根因：不是数值填小，是产出数量不确定
（"1 块晶体磨几袋粉没定死"）。期望值算不出来，必然有一档被支配。

三选一（按改动量）：

  • A（最小，推荐）：粉末袋不给钱，给 ExchangeCumulativePoints。攒点数换独占货物。
    价格比较自动失效，报表都不用重调。
  • B：转化率写死成表字段（1 晶体 = N 袋粉），硬约束
    袋单价 × N > 晶体单价 × (1 + 加工时间折损)，写进 CI。
  • C：稀缺性错位——硬晶体随便卖，粉末袋是唯一能进某条兑换链的东西。

原则：同一件东西不要有两个可比的售价；不同售价必须挂不同的渠道、耗时或独占性。
